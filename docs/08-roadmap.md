# 后续可扩展方向

按「投入产出比」排序，不按技术新颖度排序。

---

## P0：让现有能力更可靠

### 1. 视觉回归测试

**问题**：模板或渲染器改动后，肉眼很难发现"某封邮件的间距变了"。
这是内容系统最容易出回归的地方——渲染器有200 多行 HTML 生成逻辑。

**方案**：

```python
# backend/tests/test_visual.py
@pytest.mark.parametrize("template_key", ALL_TEMPLATE_KEYS)
def test_template_render_snapshot(template_key, snapshot):
    html = render(builtin_schema(template_key))
    snapshot.assert_match(html, f"{template_key}.html")
```

配合 Playwright 截图：

```python
@pytest.mark.parametrize("viewport", ["desktop", "mobile"])
def test_template_screenshot(template_key, viewport, screenshot):
    page.goto(f"/preview/{template_key}")
    screenshot.assert_page(f"{template_key}-{viewport}.png")
```

**收益**：模板改动导致视觉漂移时CI 直接失败，而不是等运营发现。
**成本**：约 2 天（含快照基线管理）。

### 2. LLM 通道可观测性

**问题**：现在只有总延迟和 `llm_error`。LLM 逐渐变慢或返回质量下降时，
无法及时发现——只会表现为"识别越来越不准"。

**方案**：
- 每次 LLM 调用记录：`prompt_tokens` / `completion_tokens` / `finish_reason` / 原始输出
- 增加滑动窗口统计：解析失败率、超时率、平均重试次数
- `intents` 表加索引，按时间聚合分析

**收益**：把"感觉不准"变成"这周解析失败率从 0.2% 涨到 8%"。

### 3. 意图词典的可视化调优

**问题**：调优只能靠看 `rule_evidence` 一条条猜。
真实场景下几十个词条互相影响，很难点出到底该调哪个。

**方案**：
- 用示例语料库批量跑识别，看混淆矩阵
- 界面展示「该词条在最近 N 次识别中贡献了多少正确/错误判断」

**收益**：词典迭代从拍脑袋变成数据驱动。

## P1：填补功能缺口

### 4. 视觉拖拽编辑器

**问题**：当前通过「左栏点击 + 右侧属性面板」编辑。
做精细排版（调整区块顺序、微调间距）时不够直觉。

**方案**：引入拖拽排序（基于现有 `moveNode()`），
预览 iframe 内直接支持拖动区块，不引入 GrapesJS 这类重量级方案——
Block Schema 已经是结构化的，不需要通用网页编辑器。

**收益**：保留"预览=导出"的唯一性，同时获得所见即所得的拖拽体验。
**成本**：约 1 周。

### 5. A/B 与内容变体

**问题**：同一封邮件只能有一个版本发出去，无法做标题 A/B 测试。

**方案**：

```sql
-- content_variants
content_id, variant_key, schema, weight, is_control
```

- 一个 content 下多个 variant
- 导出/投递时可选择「主版本」或「全部变体」
- 变体间可做diff（复用 `schema_diff()`）

**收益**：把系统从"内容生产工具"变成"内容实验平台"。
**成本**：约 1 周（数据模型 + 路由 + 界面）。

### 6. 智能 lint 修复

**问题**：lint 告诉运营"缺少 alt"，但没告诉他该填什么。

**方案**：为 error 级问题提供一键修复：

| 问题 | 自动修复 |
|---|---|
| `missing_subject` | 用内容名 + 场景生成候选主题（3 选1） |
| `missing_unsubscribe` | 从项目配置读退订链接模板 |
| `subject_too_long` | 截断到 35 字并提示 |
| `img_no_alt` | 用 `alt` 生成规则推导（如产品名 + 场景） |
| `no_meta_desc` | 从首段文本提取 |

**收益**：把"阻断导出"从障碍变成引导。
**成本**：约 3 天。

### 7. 素材库（DAM）集成

**问题**：图片全靠外链，运营要找设计单独出图。

**方案**：通过 MCP 接入 DAM：
- 意图识别时如果 `component_hints` 含 `image`，列出可用素材
- 编辑器里可搜索并插入素材
- 导出时可选「下载并内联 base64」或「保留外链」

**收益**：打通"内容 + 素材"两个孤岛。
**成本**：取决于 DAM 的 API，约 3~5 天。

## P2：架构级演进

### 8. Mautic 双向同步

**问题**：现在是单向投递。运营在 Mautic 后台改了邮件，本系统不知道。

**方案**：
- 定期拉取 Mautic 侧变更，对比 `customHtml`，有差异时提示
- 提供「从 Mautic 导入」把 Mautic 版本收成 Block Schema（逆向解析 HTML）
- 双向绑定记录 `mautic_asset_id` + `mautic_last_synced_at`

**难点**：HTML → Block Schema 的逆向解析天然有损。
**建议**：只做「差异提示 + 单向导入」，不做自动双向合并。

### 9. 多租户与权限模型

**问题**：当前只有角色级权限（admin/editor/designer/viewer），
没有「谁能改哪些项目」的边界。

**方案**：

```
tenant ──► project ──► content
   │           │           │
   └── users  ─┴───────────┘
       └─► role_binding(tenant_id, user_id, role, scope)
```

- 内容级权限：`viewer` 只能看，`editor` 能改，`admin` 能发布/归档
- 项目级权限：某运营只能改自己负责的项目

**收益**：支持外部客户隔离（多租户 SaaS 化）。
**成本**：约 1.5 周（数据模型 + 权限中间件 + 界面）。

### 10. 实时协同编辑

**问题**：两人同时编辑同一内容时，只能靠草稿锁 + 乐观锁串行处理，
后者收到 409 后要手动刷新。

**方案**：CRDT（如 Yjs）——但这会与「版本只追加」的审计模型冲突：
CRDT 是就地合并，不产生线性版本链。

**取舍**：更可能的选择是**不做全实时**，而是用
[Automerge](https://automerge.org/) 的"保存时合并"模式——
编辑时独立操作，保存时做三方合并，仍产生新版本。

**成本**：约 3 周。**建议**：先不做，用乐观锁 + 草稿锁覆盖大部分场景。

### 11. 渲染服务分离

**问题**：渲染在 API 进程内同步执行。大内容（几十个区块）渲染耗时可观，
在多 worker 部署下会占用 API worker。

**方案**：拆出独立渲染服务（可基于 Playwright 做更真实的预览，
或用 Rust/Go 重写渲染器）。

**触发条件**：单内容渲染 >500ms，或 API P95 延迟受渲染影响。
**建议**：先监控，不提前优化。

## P3：生态

### 12. 官方组件市场

组件包已经有了（`plugin.json` + MCP），缺的是分发。

**方案**：
- 组件注册中心（按类别/标签检索）
- 一键安装 + 版本更新 + 依赖解析
- 组件质量分（lint 通过率、下载量、更新时间）

**收益**：让「快速调用组件生成内容」从内部能力变成生态。

### 13. 提示词资产化

意图识别的 system prompt 写死在代码里。不同业务线（赛事/旅游/电商）
需要不同的场景词典与追问策略。

**方案**：把提示词与词典做成「意图配置」：

```yaml
# intent_profiles/waterbomb.yaml
name: WATERBOMB 赛事
scenarios: [promo, schedule_change, lead_gen]
extra_keywords: {...}
llm_prompt_override: |
  你是 WATERBOMB 音乐节的营销内容助手...
  重点关注：阵容、场次、购票渠道
```

**收益**：不同项目可独立演进识别策略，不必改代码。

### 14. 分析闭环

**问题**：内容导出后，投放效果如何？系统不知道。

**方案**：
- 导出时生成带 UTM 的追踪链接
- 对接 GA4 / 第三方报表 API
- 回填到内容上：「这封邮件的打开率 34%，点击率 8.2%」
- 反哺：把高转化结构沉淀为「有效模板」

**收益**：从「内容生产工具」升级为「内容效果优化工具」。
**收益最高的方向**——但依赖外部数据源，需要先谈成数据接入。

## 一句话判断

这个系统当前的价值在**「把一句话变成可交付的内容」**。
后续所有方向里，最能放大这个价值的是：

- **降低摩擦**（3、4、6）——让识别更准、编辑更顺、导出更少阻断
- **闭环反馈**（14）——让系统知道什么内容有效，反过来指导生产

而 10（实时协同）、11（渲染分离）这类技术优化，
在当前规模下收益有限，不建议提前投入。
